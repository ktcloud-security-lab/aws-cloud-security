# 404 Desk · AWS 클라우드 보안 프로젝트

404 Desk는 404팀이 AWS에서 운영하는 **문의 관리 웹 서비스**입니다. KT cloud TECH UP PROJECT 3에서 이 서비스를 바탕으로 클라우드 환경을 구축하고, IAM 접근 통제, 네트워크 보안, 위협 탐지와 취약점 조치를 실습했습니다.

**[🌐 404팀 프로젝트 사이트](https://team404.kro.kr/)** · 기본 프로젝트 기간 2026.11.04~12.01

## 주요 기능 ✨

| 기능 | 설명 |
| --- | --- |
| 문의 관리 | 팀원이 로그인해 문의를 작성하고 자신의 문의와 답변을 조회합니다. |
| 관리자 답변 | 관리자가 문의에 답변하고, 문의 작성자가 답변을 확인합니다. |
| 사용자별 접근 제한 | 다른 팀원의 문의를 보거나 일반 사용자가 답변을 등록하는 시도를 제한합니다. |
| 직무별 AWS 접근 통제 | IAM 그룹 정책과 EC2 태그를 기준으로 관리 권한과 서버 접속 범위를 제어하는 구조를 설계했습니다. |
| 위협 탐지와 관제 | AWS WAF와 Snort IPS를 구성하고 CloudWatch 로그와 경보로 정책 동작을 확인합니다. |
| 네트워크 보안 자동점검 | Python과 Boto3로 AWS 보안 그룹과 네트워크 접근 정책을 점검합니다. |

### 1. AWS 환경 구축 및 서비스 확장

### 2. IAM 사용자 및 권한 관리

팀의 **AWS IAM 접근 권한 매트릭스**와 **IAM 그룹별 권한 정의서**를 기준으로 직무별 권한을 설계했습니다. AWS 리소스 관리·조회, SSM 서버 접속, 서버 내부 Linux 권한은 각각 해당 설정에서 제어합니다.

| 직무 | IAM 그룹 | SSM 접속 설계 | 접속 Linux 계정 |
| --- | --- | --- | --- |
| 총괄 | `404-Admin` | 전체 | `admin` |
| 개발 | `404-Developer` | WEB·WAS | `developer` |
| 운영 | `404-Operator` | WEB·WAS·DB | `operator` |
| 네트워크 | `404-Network` | NAT | `network` |
| 보안 | `404-Security` | IPS | `security` |
| 관제 | `404-Monitoring` | 서버 접속 제한 | 미부여 |

- **직무별 권한** — 개발은 WEB·WAS 배포, 운영은 서비스와 DB 운영·백업, 네트워크는 VPC·라우팅·SG·NACL 관리, 보안은 WAF·IPS 정책 관리, 관제는 로그 분석과 CloudWatch 경보 관리를 담당합니다.
- **서버별 접속 통제** — EC2의 `ServerRole` 태그로 SSM 접속 대상을 제한하고, Session Manager Run As와 Linux 계정·sudo 정책으로 접속 후 작업 권한을 구분합니다. 관리 범위를 결정하는 태그 변경은 별도 정책으로 제한하는 설계입니다.
- **검증 기준** — 개발자의 WEB·WAS 접속은 허용하고 DB·NAT·IPS 접속은 거부합니다. 관제는 CloudWatch·CloudTrail 조회 및 경보 관리가 가능하고 서버 접속·WAF 변경·로그 삭제는 거부돼야 합니다. 팀 권한 정의서의 허용·거부 항목을 기준으로 실제 적용 상태를 확인합니다.

### 3. 클라우드 네트워크 보안 및 접근 통제

- **서비스 진입점** — ALB가 웹 요청을 받고 WEB에 전달합니다. WEB의 인바운드는 ALB 보안 그룹을 기준으로 제한했습니다.
- **내부 통신** — WAS의 애플리케이션 포트는 WEB에서 들어오는 접근으로 제한하고, MySQL은 WAS에서 들어오는 연결을 중심으로 허용했습니다. 보안 그룹과 서브넷 NACL을 함께 검토해 불필요한 내부 접근을 줄였습니다.
- **아웃바운드와 관리 접속** — NAT 인스턴스가 내부 서버의 외부 통신을 지원합니다. 서버 관리 접속은 SSM을 기준으로 설계했으며, 외부에서 DB와 SSH에 직접 접근할 수 있는지는 검증 항목으로 관리합니다.
#### 네트워크 보안 자동점검

기본 프로젝트의 도전 과업으로 **Python과 Boto3(AWS SDK for Python)**를 사용해 AWS 보안 그룹과 네트워크 접근 정책을 점검하는 스크립트를 구현했습니다. 불필요한 외부 접근 허용이나 개방 포트를 확인할 때 활용했으며, 진단 도구와 점검 범위는 네트워크 취약점 점검보고서에 기록했습니다.

### 4. 보안 장비 구축 및 정책 고도화

| 구성 | 적용 및 확인 내용 |
| --- | --- |
| AWS WAF | ALB에 웹 보안 정책을 연결해 SQL Injection 등 웹 요청을 검사합니다. WAF 처리 결과는 CloudWatch에서 확인합니다. |
| Snort IPS | 전용 EC2에서 경유 트래픽을 인라인으로 검사합니다. 기술문서에는 서비스 실행과 인라인 구성을 확인한 기록이 있으며, 경고와 차단을 각각 기록합니다. |
| 로그·알림 | 보안팀이 정책을 관리하고 관제팀이 로그와 경보로 결과를 확인합니다. 네트워크 조치보고서에는 통제된 테스트에서 WAF 차단 지표가 임계값을 넘어 CloudWatch 경보가 ALARM으로 전환된 기록이 있습니다. |
| 운영 검증 | 방화벽·라우팅·탐지 정책 변경 후 정상 서비스와 필요한 관리 접속을 재확인합니다. |

## 팀 공통 과업 · 취약점 점검 및 조치

**주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드**를 참고해 NAT, DB, WEB, IPS, 네트워크 및 Linux 계정 관리를 점검했습니다. 초기 진단, 변경 영향 검토, 설정 조치, 재점검 순서로 진행했으며 부분 개선과 보류도 결과에 기록했습니다.

| 점검 대상 | 첨부 보고서에서 확인한 내용 |
| --- | --- |
| NAT | 43개 항목을 점검했습니다. 동일 조치보고서에서 취약 항목은 **15개 → 4개**로 줄었습니다. 호스트 방화벽, 서비스, 패치 및 로그 설정을 개선하고 외부 통신을 재확인했습니다. |
| DB | 진단보고서 기준 50개 항목 중 34개 양호, 16개 취약이었습니다. 조치보고서에는 감사 로그 접근 제한, SG·NACL 연계, 조치 항목 재확인 및 보류·부분 적용 사항이 기록돼 있습니다. |
| WEB | 점검·조치 결과보고서는 초기 취약 19개를 기록합니다. 계정 관리, 파일 권한 및 웹 서비스 설정을 점검하고 변경 증적을 정리했습니다. |
| IPS | 진단보고서의 55개 항목 중 27개 양호, 26개 취약, 2개 해당 없음이었습니다. 조치보고서는 별도 조치 대상을 다루며 설정·파일 권한 등의 항목별 재확인 결과를 기록합니다. |
| 네트워크 | 32개 항목을 점검했습니다. 초기 취약 22개 가운데 **15개가 양호로 전환**됐고, 5개는 부분 개선, 2개는 보류입니다. 동일 보고서 기준 점수는 **65/240 → 180/240**입니다. |
| Linux 계정 | NAT·DB·IPS·WEB의 계정관리 조치 대상 24개를 서버별로 기록했습니다. root 직접 SSH, 비밀번호 정책, 계정 잠금 및 세션 종료를 검토했습니다. NAT·IPS 운영 환경의 계정 잠금을 시험했고, DB는 시험 서비스에서 잠금 동작을 확인했습니다. |

대상별 점검 범위가 다르고 계정관리 항목이 서버 보고서와 겹치므로, 수치는 각 보고서의 범위에서 봅니다.
