# 주기적 보안 패치 관리 절차

## 1. 관리 목적

보안장비 및 운영체제의 알려진 취약점을 예방하고 신규 보안 위협에 대응하기 위해 정기적인 보안 패치 및 벤더 권고 확인 절차를 수립한다.

## 2. 점검 대상 및 주기

| 점검 대상 | 점검 주기 | 관리 방법 |
|---|---|---|
| Ubuntu OS 보안 업데이트 | 매일 | 자동 보안 업데이트 |
| OS 패치 적용 이력 | 주 1회 | 업데이트 로그 확인 |
| Snort 엔진 버전 | 주 1회 | 설치 버전 및 벤더 권고 확인 |
| Snort 공식 탐지 룰 | 주 1회 | 신규 룰 및 갱신 여부 확인 |
| AWS WAF 관리형 규칙 | 월 1회 | 기본 버전 및 변경 사항 확인 |
| 벤더 보안 권고 | 주 1회 및 수시 | 공식 보안 공지 확인 |
| 기술 지원 종료 여부 | 월 1회 | 제품 지원 정책 확인 |

## 3. 보안 패치 적용 절차

1. 현재 설치된 엔진 및 패키지 버전을 확인한다.
2. 제조사의 보안 권고 및 신규 패치 정보를 확인한다.
3. 패치 적용 필요성과 서비스 영향도를 분석한다.
4. 기존 정책 및 설정 파일을 백업한다.
5. GitHub Issue를 통해 변경 요청을 등록한다.
6. 테스트 환경에서 패치 및 정책 호환성을 검증한다.
7. 담당 팀원의 검토 및 승인을 받는다.
8. 협의된 유지보수 시간에 패치를 적용한다.
9. 필요한 경우 시스템 또는 서비스를 재시작한다.
10. 보안장비 및 전체 서비스의 정상 동작을 검증한다.
11. 패치 적용 결과를 PATCH_HISTORY.md에 기록한다.

## 4. 패치 적용 후 검증 항목

- 운영체제 및 보안장비 버전
- Snort 설정 유효성 검사
- Snort IPS 서비스 실행 상태
- NFQUEUE 패킷 검사 및 전달 상태
- Snort 탐지 로그 생성 여부
- AWS Systems Manager 원격 접속
- 웹사이트 및 이메일 인증 기능
- CloudWatch 로그 수집 상태

## 5. 장애 발생 시 대응

패치 적용 이후 장애가 발생할 경우 사전에 백업한 정책 및 검증된 이전 버전을 활용하여 복구한다.

복구 이후 서비스 정상 동작 여부를 확인하고 장애 원인과 복구 결과를 기록한다.

## 6. 예외 관리

즉시 적용하기 어려운 패치 또는 지원 종료 제품은 미조치 사유, 발생 가능한 위험, 대응 계획 및 조치 예정 일정을 기록하여 관리한다.
